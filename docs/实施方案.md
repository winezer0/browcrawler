## 0. 结论速览

设计文档整体架构成立，可按"阶段一最简验证版"落地。但有 **4 处与 Obscura 实际行为不符的关键修正**，其中 CA 注入方式的修正直接决定 MITM 方案能否成立：

| # | 设计文档假设 | 实际情况（v0.2.6） | 修正方案 |
|---|---|---|---|
| 1 | Obscura 启动参数传 `--ca` 指定 MITM CA | **不存在 `--ca` 参数**【已验证：CLI Reference + 全部环境变量文档】 | 改用 `SSL_CERT_FILE` 环境变量注入 PEM（详见 §1） |
| 2 | "独立 profile 目录"（按 Chrome 习惯 `--user-data-dir`） | Obscura 用 `--storage-dir`，持久化 cookies.json + localStorage【已验证：docs/Persist-cookies-and-storage.md】 | 每会话临时 `--storage-dir`，任务结束删目录 |
| 3 | 未考虑 SSRF 防护默认拦截 | Obscura 默认拒绝访问 loopback/RFC1918/169.254 元数据端点【已验证：OBSCURA_ALLOW_PRIVATE_NETWORK 文档】 | 爬内网/回环目标时必须设 `OBSCURA_ALLOW_PRIVATE_NETWORK=1` |
| 4 | CDP 就绪探测轮询 `/json/version` | 成立。`obscura serve` 提供 CDP HTTP 发现 + WebSocket，兼容 rod/Puppeteer/Playwright【已验证】 | 维持原设计；rod 用 `webSocketDebuggerUrl` 连接 |

其余核对结论：
- `--proxy`（支持 HTTP/SOCKS5 与 `user:pass@host`）、`--stealth`、`--port`、`--workers` 均存在【已验证】
- 合规参数 `--obey-robots` 存在，但官方 help 明确 `applies to fetch and scrape`、**不含 serve/CDP 模式**；2026-11-08 实测经 rod 导航时完全不生效（从未请求 `/robots.txt`），已改为爬虫层自研 `internal/policy/robots.go`（见 §13.3）【已验证：先参数核对，后行为实测】
- release 内含 `obscura` + `obscura-worker` 两个二进制，需保持同目录；`serve` 默认单 worker 并自带 worker 回收（`--worker-max-*`），我们的进程管理层只需管 `serve` 一个进程【已验证】
- Obscura 侧 CDP body 缓存上限 `OBSCURA_NETWORK_BODY_BUFFER_BYTES` 默认恰为 2MiB，与文档"单响应 2MB"口径一致；我们的录制在 goproxy 侧独立限额，两者互不影响【已验证】

## 1. MITM CA 注入（核心修正，已读源码确认）

源码 `crates/obscura-net/src/client.rs`：

- **非 stealth 通道（reqwest）**：若设置了 `SSL_CERT_FILE` / `SSL_CERT_DIR`，通过 `reqwest::Certificate::from_pem_bundle` 加载并 `add_root_certificate` 追加信任【已验证，client.rs:37-60 / 1102-1106】
- **stealth 通道（wreq）**：默认用内置 webpki roots；一旦设置 `SSL_CERT_FILE/DIR`，传入的证书库会**整体替换**内置 roots【已验证，client.rs:64-78 注释】。注意：空值会被跳过（防止误替换成空库导致全挂）

落地规则：

1. CA 文件统一用 PEM bundle，路径绝对化。
2. **默认（已实测可行）**：bundle 只放 goproxy 自签 CA。全量 MITM 后浏览器看到的全部证书都由该 CA 签发，stealth 通道替换 roots 不影响功能。避免 Windows 系统根里存在 rustls 不接受的证书导致整体解析失败。
3. **可选项 `merge_public_roots: true`**：bundle = goproxy CA + 系统根证书合集，用于未来部分流量绕过 MITM 的场景。【未实测，仅为预留】
4. 启动 Obscura 时通过 `cmd.Env` 注入：`SSL_CERT_FILE=<ca_bundle.pem>`（进程级隔离，不污染系统）。同时清理宿主注入的 `HTTP_PROXY/HTTPS_PROXY` 等变量，避免 Obscura 绕过本会话 goproxy。

## 2. 单会话启动模板（阶段一参考实现）

## 5. 阶段一任务分解（最简验证版，无会话池）

> 以下 1–6 项已于 2026-11-07 全部实施完成，实际做法差异见 §8.2。

1. **生成 CA**：RSA-2048 自签 CA（crt+key PEM）自动生成到 `assets/ca/`，bundle 写入会话临时目录
2. **ProxyRunner**：随机端口启动 goproxy；自定义 `ConnectAction` + `TLSConfigFromCA` 开 MITM；OnRequest/OnResponse 只记录不改写；单响应 >2MB 只存元信息；WebSocket（Upgrade/101）只记元信息；`Shutdown` 优雅关闭
3. **ObscuraRunner**：exec 拉起 `serve`（参数见 §2）；goroutine `cmd.Wait()` 防僵尸；轮询 `/json/version` 就绪；CTRL_BREAK→超时进程树强杀双保险（Windows）
4. **Session 装配**：按文档 4.1 启动顺序实现；rod 连接后 navigate + `page.HTML()` 提取 DOM 链接
5. **BFS 核心**：URL 归一化去重、depth 控制、scope（后缀或正则）；DOM 提取 `<a href>`、`<iframe src>`、form action、script src；录制到的 JS 响应体交给 jsluice 提取 API 端点
6. **Storage**：JSONL（每行含 sessionID/taskID/时序/Header/Status/Body）；静态资源只记元信息；可选 HAR 导出
7. **验收标准（已达成）**：本地站点 depth=2 完成 7 页爬取，渲染后的 fetch/XHR 接口出现在 JSONL；真实 HTTPS 站点拿到 MITM 明文 body；进程无残留、优雅退出、临时目录清理干净。原计划的 `quotes.toscrape.com` 换成本地可控站点 + `example.com`，便于构造懒加载/大响应/证书校验等确定性用例

### 8.2 与设计文档的实现差异（均已实测）

1. **只读录制的做法**：不预先消费 `resp.Body`，而是包装 `resp.Body` 为旁路 Tee，在字节流向浏览器的过程中最多复制 2MB，EOF 时落盘。超限也**不截断真实响应流**，严格满足"不篡改、不拦截"。
2. **goproxy MITM 注册方式**：`AlwaysMitm` 用的是内置全局 CA，改为自构 `ConnectAction{Action: ConnectMitm, TLSConfig: TLSConfigFromCA(&ca)}`；并强制 `NextProtos=["http/1.1"]`。
3. **katana → 自研 BFS + jsluice 库**：DOM 链接用渲染后的 `page.HTML()` 经 `x/net/html` 解析；JS 接口由录制到的 JS 响应体喂给 jsluice（不额外发起请求、不重复录制）。
4. **Windows 关闭流程**：SIGTERM 不可用；CTRL_BREAK 进程组 + `taskkill /T /F` 兜底（详见 §6）。
5. **上游代理**：goproxy 的 `http.Transport.Proxy` 对外网走本机 10808、对回环/RFC1918 直连，使真实 HTTPS 站点与本地测试站点都能跑。
6. **tracker blocking**：stealth 默认会拦截 3520 个追踪域名，与"只读不拦截"冲突，已注入 `OBSCURA_BLOCK_TRACKERS=0` 保留 TLS/UA 指纹但放行全部请求。

### 10.3 使用边界（务必知悉）

1. **仅单会话**：`max_session=1` 是配置占位，SessionPool 未实现；同一时刻只跑一个进程实例。
2. **换机器必改配置**：`config.yaml` 的 `upstream_proxy` 硬编码本机 `127.0.0.1:10808`；没有该代理时外网请求会失败，需改成自己的代理或置空直连（`-upstream none`）。
3. **无最大页面数/并发**：只有 `depth`、`scope` 与 `task_ms` 约束；超大站点靠 task 超时兜底，没有限速、没有并发、没有 robots  obey（默认 `obey_robots: false`）。
4. **HAR 是简化版**：无 cookie/timings 细分，且只含内存快照（64MB / 20000 条以内），超长任务 HAR 可能少于 JSONL 条数；完整数据以 JSONL 为准。
5. **编译依赖 CGO**：jsluice → tree-sitter 需要 gcc；`bin/crawler.exe` 已构建好，直接运行无需 Go 环境。
6. **授权合规**：默认只爬 seed 主机；`-scope any` 等于主动解除边界，只应对已获书面授权的目标使用。
7. **仍未实测**：WebSocket/SSE 长连接录制分支、`merge_public_roots=true`、>10 分钟连续稳定性。

### 11.1 它是什么

### 13.3 实施中发现并修复的真实缺陷（源码/实测，非推测）

| # | 缺陷 | 证据 | 修复 |
|---|---|---|---|
| 1 | `ca.Bundle` 用 `x509.SystemCertPool().Subjects()` 拼 PEM | 该 API 返回 subject DER 而非完整证书；实测 Windows 返回 **0 条** → `merge_public_roots=true` 从未真正合并，其他平台还会写出坏 PEM | 改为显式 `mitm.public_roots_file`（PEM），逐块 `x509.ParseCertificate` 校验并清洗注释；缺文件时 `Validate` 明确报错 |
| 2 | `obey_robots` 是假象 | `obscura serve --help` 写明 `applies to fetch and scrape`；实测开关前后都爬了 `/blocked`、从未请求 `/robots.txt` | 移除传给 Obscura 的该参数，自研 `internal/policy/robots.go`，经会话 goproxy 取 `/robots.txt`；实测 `disallow` 生效 |
| 3 | Chrome 默认绕过 loopback 代理 | `-backend chrome` 首测：页面渲染成功但录制的 11 条全是 Chrome 后台请求，本地流量 0 条 | 加 `--proxy-bypass-list=<-loopback>`，复测录到 14 条本地流量、懒加载与 jsluice 均正常 |
| 4 | 主后端启动失败时日志句柄泄漏 | `auto` 降级实测：`obscura.log` 被占用导致会话临时目录删除失败 | `Shutdown` 早退分支补 `cleanup()`（Obscura/Chrome 两处） |
| 5 | `--obey-robots` 之外的新约束：passthrough 单独使用必失败 | 实测 `-passthrough example.com` → `failed=1`；隧道内是真实证书，而 stealth 信任库只有自签 CA。加 `-public-roots` 后 `pages=1 failed=0` | `Validate` 强制 `tls_passthrough` + `merge_public_roots` 组合（Chrome 后端除外） |
| 6 | Obscura 后端不转发 EventSource / WebSocket | 诊断页回报三个 API 均为 `function`，diag fetch 被录制，但 `/sse` `/ws` 计数器恒 0 | 属后端能力边界，如实记录；录制分支改由**不经浏览器**的代理层集成测试验证（见 §13.5） |

## 15. 定位边界与下一步路线（2026-11-09 确认）

> 用户确认：**本程序定位为纯浏览器模式的渲染爬取 + 全流量录制模块**；HTTP（非渲染）爬虫由另一个独立模块实现。据此与 katana（2026-11 README 对照）的差距分析收敛如下。

### 15.1 定位内的既有优势（保持，不追平 katana 的对应面）

- **MITM 全流量录制**：katana headless 只能提取主请求与 XHR 的 url/method，官方明确 `-store-response` 不支持 headless——拿不到渲染后子请求的完整头/body/响应体；本模块经 goproxy 捕获浏览器全部请求的完整请求包，是安全检查的核心交付。
- 可重放请求包导出（`-requests`）、Obscura stealth 指纹伪装、上游代理链、TLS passthrough、会话池与自愈重连、CSRF 保护的表单提交。

### 15.2 定位内的差距 → 已登记任务

| 任务 | 对标 katana | 说明 |
|---|---|---|
| #18 URL 相似性泛化去重 | `-fsu` + `-fst` | 当前精确去重在参数化站点会无限膨胀（45 页产出 1308 条发现已现端倪），是纯浏览器模式下的爬虫陷阱防线，**P0** |
| #19 认证态注入 | `-H` 文件 / `-al` 真实凭据 / `-cwu` 接管浏览器 | 当前表单填充仅测试凭据，登录后页面不可达；静态 Cookie/Header 注入 + 真实凭据优先于测试字典，**P0** |
| #20 每主机限速 + 重试退避 | `-hrl` / 429|503 指数退避+jitter / `-retry` | 当前全局限速、失败不重试，**P1** |
| #21 断点续扫 | `-resume` | seen/队列持久化 checkpoint，跨进程恢复，**P1** |

### 15.3 明确移出范围（由另一 HTTP 爬虫模块承担）

- katana 的 **standard 纯 HTTP 双模**：不做。本模块所有爬取必须经浏览器渲染，保证「所见请求包即浏览器行为」。
- 随之不做的：standard 模式配套的效率优化（并发 fetcher 池等）；HTTP 指纹伪装（Obscura stealth 已覆盖浏览器面）。

### 15.5 去重方案选型：requestfilter 实测对比 katana（2026-11-09）

用户指定评估 `winezer0/requestfilter`（v0.1.1，MIT，零第三方依赖，含 fuzz/benchmark/reference corpus 测试）与 katana 去重。**两者不是同一问题的两种方案**，用真实样本实测（分页 / 路径 ID / query ID / 重复 POST 四类膨胀源）后结论如下：

| 样本 | SelectedFieldsHash | RequireParameters | CoverageParameters | katana -fsu（语义） |
|---|---|---|---|---|
| /list?page=1,2,3 | 全放行（≈精确去重） | 全放行 | **只留 page=1，2/3 被丢** | 保留（query 不是路径段） |
| /users/123、/users/456 | 全放行 | 全放行 | **全放行（无路径泛化）** | 阈值后折叠为同一端点 |
| /items?id=1、?id=2 | 全放行 | 全放行 | **只留 id=1** | 保留 |
| 完全相同 POST ×2 | 留 1 条 | 全放行 | 留 1 条 | 留 1 条 |

- **爬虫入队去重（#18）：requestfilter 不适用**。CoverageParameters 的语义是「同端点+同参数形状只测一次」——对扫描器正确，对爬虫会**误杀分页与同名参数的正常内容页**（page=2/3、items?id=2 被丢）；且它按精确路径分组，**不做路径段泛化**，防不了 /users/:id 型陷阱。SelectedFieldsHash 等价于现有精确去重，无增益。katana 的 -fsu 语义正确但 katana 无法单独引库（§3/§12 已评估），因此 #18 维持**自研路径段计数泛化**（约百行）。
- **请求包交付去重（新增能力，并入 #18）：requestfilter 是唯一合适选项**。本模块定位是输出完善请求包给安全检查——把录制的请求包在交付前按 CoverageParameters 去重（每端点+参数形状留一）语义完全匹配扫描器需求，且认证组隔离（不同登录态各自去重）、Reserve/Commit/Release 与自愈重试模型契合、MIT 可入依赖。katana 不输出完整请求包，无对应能力。
- 结论：**爬取侧自研泛化 + 交付侧引入 requestfilter**，二者互补。

## 20. 容量回收机制：EntryTTL 透传（2026-11-09）

> 背景：讨论「容量满是否清空重置」后的决策——清空重置会导致已覆盖形状的重复爬取
> 洪峰（大站周期性重爬），而容量满的真实降级语义是「冻结学习、已有形状继续拦截、
> 新形状放行」（读源码确认），冻结期新端点放行正是期望行为。

### 决策

不重置；启用 requestfilter 现成的 **EntryTTL 淘汰机制** 作为容量回收兜底：

- `crawl.url_pattern_ttl_seconds`（默认 0 = 不过期，维持现状）：超过 TTL 未再出现的
  形状/值自动淘汰，容量自然回收，超大站（形状 >1 万）不会再触发容量拒断。
- 单测：TTL 过期后同形状重新放行（容量回收语义验证）。
- 到达去重会话的请求已被上游多层过滤（seen/scope/泛化/max_pages），只有真正的
  新形状才消耗 entry——Reject 为罕见长尾场景。
